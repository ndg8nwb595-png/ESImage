# 排错 Tips

- **`gh` 报 401 Bad credentials**：不是仓库问题，是本地 keyring token 失效。执行 `gh auth login -h github.com` 后重试；`gh auth status` 可确认。
- **`gh` 能读不能写、报 403 Resource not accessible**：fine-grained PAT 的仓库权限不足。需在 token 设置里勾选对应权限（如 Issues: Read and write），或改用 classic token 的 `repo` 范围。
- **用户提供的 `.env` 键名可能是 `GITHUBTOKEN` 而非 `GITHUB_TOKEN`**：解析时不要假设键名，用 `sed 's/^[^=]*=//'` 去掉任意键前缀更稳；只打印前缀和长度，不要回显完整 token。
- **`git push` 报 403 Permission denied（账号是仓库所有者）**：不是身份问题，是 PAT 缺 **Contents: Read and write**。Git 用 GCM（`credential.helper=manager`）而非 gh 的凭据；改用带 `repo` 范围的 token，或 `gh auth login -w` + `gh auth setup-git` 让 gh 接管。旧凭据可能被 GCM 缓存，必要时 `git credential-manager erase`。
- **Windows 下多行正文传给 `gh issue create`**：在 Bash 工具里用 heredoc；在 PowerShell 里用单引号 here-string（`@'...'@` 且结束符顶格）。
- **GitHub 的 issue 与 PR 共用编号**：遇到 `#42` 先 `gh pr view 42`，失败再 `gh issue view 42`。
- **子 issue 需要 gh 2.94+**：本机为 2.93，需用 `gh api` 的 `sub_issues` 端点，或在正文写 `Part of #<parent>`。
- **阻塞关系用 database id**：`gh api repos/<owner>/<repo>/issues/<n> --jq .id`，不要传 `#number` 或 `node_id`。
- **领域文档缺失不要报错**：技能约定是静默继续，避免在仓库尚未建立 glossary 时刷噪音。
- **AskUserQuestion 的 preview 在用户端会折叠**：用户看不到 preview 内容。关键信息必须写进选项 description 或聊天正文，不能只放在 preview 里。
- **用户偏好逐题选择**：一次只问一个决策，每题给 3 个方案并标注推荐项，让用户用键盘选；不要一次抛出多个待答问题。
- **访谈顺序**：先定产品形态、范围、角色、技术栈等上层决策，再问页面与字段细节；新增需求会与既定文档结构冲突，需回头对齐后再写文档。
- **PRD 中的“待确认项”要显式列出**：如设计 Skill 未产出、豆包模型名未实测、API Key 未配置，避免把假设写成结论。
- **术语表双处同步**：`GLOSSARY.md` 是唯一来源，`AGENTS.md` 的「Domain glossary」只是镜像。新增或修改术语时先改 `GLOSSARY.md`，再同步 `AGENTS.md`，否则两处会漂移。
- **布局变更要跨文档同步**：工作台从两栏改三栏时，需同步 `0-系统汇总prd.md` 的 5.2 与验收表、`2-用户端创作工作台prd.md` 的 2.1/2.2/第 10 章/验收、`3-Agent会话交互prd.md` 的会话列表位置；改完用 Grep 搜旧词（如「左右分栏」「左侧聊天区」）确认无残留。
- **参数模型变更要全库搜旧词**：删除「产出类型」、改「风格自由文本」、调整张数时，影响 0/2/3/4/5/6/7/9/10 号文档与接口示例、数据模型、种子数据。改完用 `Grep` 搜 `产出类型|主图 4|详情图 6|8 种|style_id|output_type|/styles|风格配置`，确认只剩“不提供/不维护”这类否定表述。
- **PRD 交叉评审先查“同一概念的四处定义”**：表清单（0/10）、接口清单（9）、枚举（10）、状态机（0/4）、权限点（6/10）。一处改动没同步，就会出现“接口有字段、数据库没字段”这类阻断问题。
- **状态机要做可达性检查**：画出初始态到所有终态的路径。例：`full` 批次创建时 `completed_count=1`，若 5 张详情全失败，按“全部失败→failed”永远到不了 `failed`，只能 `partially_failed`。
- **并发限制要区分“进行中”和“待确认”**：`sample_ready` 是等用户操作，不是 Worker 在跑；若并发规则把它算作进行中，用户点“重新生成示例”会被自己锁死。
- **API 字段必须能落到数据模型**：逐个核对接口响应字段（如 `stage`）与表字段；反之核对“数据模型有、接口无”（如 `size_presets`、提示词版本引用）。
- **文档中的“桶”和“前缀”不要混用**：MinIO 已改为单桶 `esimage` + `archive/` 前缀，术语表若仍写“归档桶”，会与 0/10 号冲突。
- **重复清单要设唯一来源**：8 Agent、23 个权限点、状态枚举、菜单清单都在多份文档重复；评审时以一份为基准，其余标“同步镜像”。
- **重试策略与超时要一起改**：把 Agent 重试从 1 次改成 10 次时，必须同步整批超时（600→1800 秒）、单张生图尝试次数、部分失败语义，以及 0 号汇总与 4 号生图文档；否则 10 次重试会被 10 分钟超时提前截断。
- **模板是整套模板**：固定 1 主图 + 5 详情图下，模板定义整套 6 张的视觉体系，不携带图片角色或尺寸；不要再给模板加 `image_role`。
- **表数量是硬编码**：0 号 §9.2 表清单、10 号 §1.2/§12、种子数据都写死表数量/清单；新增 `size_presets` 这类表时要一起改，并同步验收项。
- **模型配置是三件套**：`text_model`、`image_model`、`vision_model` 分属文本、生图、质量审核；新增视觉审核时必须同步 4/8/10/0/9 号文档与接口示例。
- **平台规则不建表**：平台规范规则（尺寸、违禁词、类目）写进 `platform_rule` 系统提示词，通过提示词版本管理维护；`{{platform_rules}}` 从该提示词读取，不要再加 `platform_rules` 表。
- **localStorage 方案要写清限制**：参数与上传图 ID 只存前端时，换设备/清缓存会丢；必须补 `GET /uploads/{id}` 恢复缩略图，并在 PRD 风险表标注，避免被当成“服务端持久化”。
- **首条会话要原子创建**：聊天/生成接口允许 `session_id` 为空，后端在同一事务内建会话 + 写消息/批次，并用 `client_message_id` 去重；不要让前端先建空会话再清理。
- **移动 PRD 前先全库搜文件名**：`docs/prd/1-登录界面prd.md` 被 0 号索引与 6 号关联文档引用；移动后必须同步相对路径，否则索引断链。用 `grep -rn` 验证无旧路径残留。
- **“最小 demo”不是“PRD 全做”**：先划出能完整演示主流程的最小闭环，再列出明确不做的项（Redis、Alembic、管理后台、超管种子）；取舍写进 README，避免后续把 demo 简化当成正式实现。
- **登录接口与 `/auth/me` 的 user 结构不同**：1 号登录响应把 `roles`/`permissions` 内嵌在 `user` 里，9 号 `/auth/me` 顶层返回 `roles`/`permissions`；前端必须归一化，接口文档要写明。
- **禁用账号的 403/401 口径有冲突**：1 号 §5.4 说 403 不跳登录，§10.10 说禁用后回登录；最小 demo 采用 `403 + 20004` 且前端对 20004 特判回登录，正式实现前需统一。
- **记住我只改 exp**：24h/7d 由后端签发 JWT 时写入 `exp`，不要引入 refresh token 或前端额外保存密码。
- **最小 demo 的审计动作码是临时约定**：`auth.login`/`auth.logout` 需与 8 号操作日志表统一后再固化。
- **再次移动 PRD 要全库搜引用**：2 号 PRD 移入子文件夹后，0/3/4/5 号文档都有引用；改完用 `grep -rn "2-用户端创作工作台prd" docs` 验证，注意文件夹内 README/接口文档用相对文件名是正常的。
- **聊天参数 `params` 不要混入 `upload_ids`**：PRD 9 的聊天 `params` 只有 `product_name`/`style_text`/`width`/`height`/`template_id`；上传图只随生成请求提交。示例容易复制粘贴带错，改完要单独 Grep `upload_ids` 确认只出现在生成接口。
- **最小 demo 要先定“不做什么”**：工作台最容易把模板、尺寸、取消、重试、ZIP、历史页都拉进来；先写清不做项与替代方案（固定尺寸、占位图、桩聊天），才能保证 7 个切片可独立验收。
- **本地文件 tickets 也按依赖排序编号**：01 无阻塞、07 在链尾；并行分支（04 与 05）不要硬连成串行，否则会误判实现顺序。
- **demo 接口文档要单独列“与正式 PRD 的差异”**：如新增预览/上传内容接口、`session_id` 可空、`last_message_preview` 字段；不列差异，后续会误以为 PRD 9 已定义。
- **错误码 HTTP 状态要逐表核对**：`30016` 在分接口表与总表曾出现 400/404 不一致，统一按 PRD 9 取 404。
- **demo 拆解要先查已有 demo 的重叠**：3 号会话 PRD 与 2 号工作台的 04 切片大量重叠（会话列表、首条消息建会话、SSE 骨架、自动命名、幂等、断线重试）；拆 3 号 demo 时先读 2 号 issues，只列增量，避免重复 ticket。
- **SSE 幂等要定义“重放”形态**：PRD 只写“直接返回已保存消息”，在 `Accept: text/event-stream` 下必须明确是 JSON 还是重放事件；demo 采用 `meta.duplicate=true` + 一次完整 `delta` + `done`，并列为待确认项。
- **前端本地状态不要假装有数据库枚举**：消息“已取消”在 `chat_messages.status` 中没有对应值；demo 只做前端中止展示，刷新后按 `sending/done/failed` 展示，不要私自新增枚举。
- **超时收敛要指定执行方**：PRD 只写“处理中的消息若已超时，标记失败”；接口文档必须写明阈值（demo 120 秒）与执行时机（消息分页时惰性标记），否则前后端会各写一套。
- **需求变化比对要落到字段**：PRD 只写“风格/卖点/尺寸”，接口文档要明确取哪张表的哪个快照字段、卖点是否忽略顺序，避免“语义相同但字符串不同”误报。
- **跨 demo 的 additive 字段要标注兼容**：3 号给 `done` 增加 `requirement_changed`、给 `meta` 增加 `duplicate`，要在接口文档“与 2 号差异”里写明是兼容新增，避免 2 号实现方以为契约变了。
