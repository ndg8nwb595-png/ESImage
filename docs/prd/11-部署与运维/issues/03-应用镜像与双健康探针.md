# 03: 应用镜像与双健康探针

**What to build:** 四个应用容器（backend、frontend、worker、beat）可以按 11 号拓扑启动；backend 提供两个健康探针——`GET /api/health` 保持 11 号原文的裸结构供容器与网关探活，`GET /api/v1/health` 返回 9 号统一响应。两个探针共用同一次依赖检测，并发检查 PostgreSQL、Redis、MinIO；全部正常返回 200，任一不可用返回 503 `degraded`，并在恢复后无需重启自动回到 200。

**Blocked by:** 02 迁移、种子与初始超管

**Status:** ready-for-agent

- [ ] backend 镜像基于 Python 3.11，使用 FastAPI + uvicorn；进程以非 root 用户运行；镜像内不含 `.env`、密钥或调试配置；监听容器内 8000，不发布宿主机端口。
- [ ] frontend 使用多阶段构建 + `nginx:stable`，监听容器内 8080；当前提供静态占位页，`GET /` 返回 200；业务页面由 1~8 号 demo 后续替换，不在此切片实现。
- [ ] worker、beat 复用 backend 镜像；worker 并发数读取 `WORKER_CONCURRENCY`（默认 4）；beat 时区为 `Asia/Shanghai`；两者只在内网运行，不发布端口。
- [ ] backend 的 Compose 依赖为 `postgres`、`redis`、`minio` 均 `service_healthy`；worker/beat 依赖 backend `service_started` 与 Redis `service_healthy`；启动顺序符合 11 号 §4.2。
- [ ] `GET /api/health` 不鉴权、不接受参数、不缓存；全部正常时返回 HTTP 200：`{"status":"ok","checks":{"database":"ok","redis":"ok","minio":"ok"}}`。
- [ ] 任一依赖不可用时返回 HTTP 503：`{"status":"degraded","checks":{"database":"ok","redis":"error","minio":"ok"}}`；三项检查都返回各自状态，不因第一个失败而短路。
- [ ] `GET /api/v1/health` 与裸探针共用检测结果：正常时返回 HTTP 200 `{code:0,message:"ok",data:{status:"ok",checks:{...}}}`；降级时返回 HTTP 503 `{code:50001,message:"服务依赖不可用",data:{status:"degraded",checks:{...}}}`。
- [ ] 检测规则：数据库执行轻量查询、Redis 执行 `PING`、MinIO 检查 `esimage` 桶存在；三项并发执行，单项超时 2 秒，整体不超过 5 秒。
- [ ] 依赖恢复后，下一次请求立即返回 200，不需要重启 backend；降级期间容器不退出。
- [ ] 响应不包含堆栈、SQL、DSN、内部地址、密钥或上游原始错误；`APP_ENV=production` 时关闭调试与详细错误回显。
- [ ] 两个健康接口均设置 `Cache-Control: no-store`；backend 的容器健康检查使用 `/api/health`，frontend 的容器健康检查使用 `GET /`。
- [ ] 停止 Redis 后两个健康接口均为 503 `degraded` 且 `checks.redis="error"`；恢复 Redis 后两个接口均恢复 200。
